# TDD Workflow Guide

> **Purpose**: 通过测试驱动开发（Test-Driven Development）的红-绿-重构循环，减少 Bug、降低技术债务、提升代码可维护性。

---

## Why TDD

**大多数 Bug 源于"先写实现、后补测试"的习惯**，而不是编码能力不足：

- 先写实现 → 测试沦为形式，覆盖不到真实场景
- 先实现后测试 → 代码已经耦合，难以编写独立的单元测试
- 没有重构意识 → 技术债务持续累积，后期修改成本指数级增长

TDD 通过强制"测试先行"，从根本上改变了开发顺序，让每一行生产代码都有明确的验证依据。

TDD 的核心收益：
- **减少 Bug**：每个行为都有对应的测试验证
- **降低技术债务**：重构阶段强制清理重复和坏味道
- **提升设计质量**：测试优先倒逼松耦合、高内聚的接口设计
- **安全重构**：有测试保护，重构时不怕改坏已有功能

---

## The Red-Green-Refactor Cycle

TDD 的核心是一个三步循环，每一步都有严格约束：

### RED —— 先写失败的测试

目标：编写一个**最小**的测试用例，运行它，确认它**失败**。

约束：
- 只写一个测试用例，不要一次写一整组
- 测试用例必须尽可能简单，只覆盖**一个**行为
- 失败的原因必须是"功能未实现"，而不是"测试写错了"

```
# 正确：最小测试用例
def test_add_todo_creates_item():
    result = add_todo("Buy milk")       # 函数还没写
    assert result.id is not None        # 预期失败：函数不存在

# 错误：一次写太多测试
def test_todo_crud():
    test_add_todo_creates_item()
    test_update_todo_changes_text()
    test_delete_todo_removes_item()
```

验证步骤：
- 运行测试，确认它**失败**
- 确认失败的错误信息符合预期（例如 `NameError: name 'add_todo' is not defined`）
- 如果测试意外通过了，说明测试本身有问题，修正测试

### GREEN —— 最小实现让测试通过

目标：用**最少**的代码让刚刚失败的测试通过。

约束：
- 只写能让当前测试通过的代码，不写任何多余逻辑
- 不关心代码是否优雅、是否高效——只求通过
- 可以硬编码返回值，只要测试允许

```
# 正确：最小实现
def add_todo(title):
    return {"id": 1, "title": title}   # 刚好能让测试通过

# 错误：过度实现
def add_todo(title):
    validate_title(title)              # 测试没要求验证
    todo = db.insert("todos", ...)     # 测试没要求持久化
    notify_subscribers(todo)           # 测试没要求通知
    return todo
```

验证步骤：
- 运行测试，确认它**通过**
- 如果测试仍然失败，检查实现是否正确匹配了测试的预期
- 所有已有测试必须保持通过（不引入回归）

### REFACTOR —— 消除重复、优化结构

目标：在测试全部通过的前提下，优化代码质量。

约束：
- **不能改变任何行为**——所有测试必须仍然通过
- 可以做的：重命名变量、提取函数、消除重复代码、改善命名、添加注释
- 不能做的：添加新功能、修改接口、改变输出格式

```
# 重构前（GREEN 阶段代码）
def add_todo(title):
    return {"id": 1, "title": title}

# 重构后（提取常量、添加类型提示）
DEFAULT_ID = 1

def add_todo(title: str) -> dict:
    """创建新的待办事项"""
    return {"id": DEFAULT_ID, "title": title}
```

验证步骤：
- 每次小改动后都运行一次测试
- 确保所有测试保持**绿色**
- 如果测试变红，立即回退到上一个绿色状态

## Coverage Target: >=80%

覆盖率是 TDD 循环的质量门禁：

| 层级 | 覆盖率目标 | 说明 |
|------|-----------|------|
| 单元测试 | >= 90% | 纯函数、工具函数、业务逻辑 |
| 集成测试 | >= 70% | API 端点、数据库操作 |
| 组件测试 | >= 80% | 前端组件渲染和交互 |
| E2E 测试 | >= 50% | 关键用户流程 |
| **总计** | **>= 80%** | 整体覆盖率基线 |

注意：
- 覆盖率是必要但不充分条件——高质量的测试比高数字更重要
- 边界条件、错误路径、空/null 输入必须覆盖
- 不要在覆盖率数字上作弊（例如写无断言的测试）

## Per-Layer Testing Strategy

### Backend 测试策略

**单元测试（pytest / vitest）**
- 纯函数逻辑：输入 → 输出验证
- 业务规则：各种条件分支全覆盖
- 数据转换：序列化/反序列化正确性
- 使用参数化测试覆盖边界值和等价类

**集成测试（pytest + 测试数据库）**
- API 端点：HTTP 状态码、响应体结构、错误处理
- 数据库操作：CRUD 正确性、事务回滚
- 外部服务：使用 WireMock / nock 等模拟外部依赖

**Mock 策略**
- 外部依赖（数据库连接池、第三方 API、文件系统）→ **必须 Mock**
- 内部模块间的调用 → **优先真实调用**，仅在测试困难时 Mock
- 时间敏感逻辑 → 使用时间注入或 freezegun / sinon fake timers
- 不要 Mock 被测试的代码本身

### Frontend 测试策略

**组件测试（vitest + React Testing Library）**
- 渲染验证：组件是否正确渲染预期的 DOM 结构
- 交互验证：点击、输入、提交等用户操作是否触发正确行为
- 状态验证：props 变化后组件是否正确更新
- 可访问性：关键交互元素是否有正确的 aria 属性

**Hook 测试（vitest + renderHook）**
- 状态初始化：Hook 初始状态是否正确
- 状态转换：调用 Hook 方法后状态变化是否预期
- 副作用：useEffect / 事件监听是否正确绑定和清理
- 边界情况：传入异常 props 时 Hook 的行为

**状态管理测试**
- Store 初始化：默认状态正确
- Action 处理：dispatch 后状态变化正确
- 异步 Action：loading / success / error 三个状态都覆盖

**E2E 测试（Playwright / Cypress）**
- 关键用户流程：登录 → 核心操作 → 登出
- 错误处理流程：网络错误、超时、权限不足
- 覆盖最重要的 3-5 条用户旅程即可

## Common TDD Mistakes

### 反模式 1：先写实现再补测试

这不是 TDD。测试必须在实现**之前**编写。补写的测试倾向于"验证实现细节"而不是"定义行为"，测试质量显著下降。

### 反模式 2：一次写太多测试

TDD 的核心节奏是**一次一个测试**。一次写 5 个测试再全部实现，你会：
- 忘记哪个测试对应哪个行为
- 容易写出过度设计的实现
- 难以定位测试失败的原因

### 反模式 3：跳过重构阶段

"测试通过了，直接下一个"——这是技术债务的主要来源。
- 重复代码不清理 → DRY 违规累积
- 糟糕的命名不改善 → 可读性持续下降
- 每次跳过重构，下一次的改动成本会更高

### 反模式 4：测试和实现紧耦合

测试应该验证**行为**，而不是验证**实现细节**。
```
# 坏测试：耦合实现细节
def test_add_todo():
    assert db.get_last_query() == "INSERT INTO todos VALUES (?)"  # 测试 SQL 细节

# 好测试：验证行为
def test_add_todo():
    result = add_todo("Buy milk")
    assert result.title == "Buy milk"  # 测试行为结果
    assert result.id is not None
```

### 反模式 5：把 RED 阶段当可选项

"这个太简单了，不用先写测试"——简单的功能也有出错的可能。TDD 的纪律性在于**所有代码**都从失败的测试开始。

## Quick Reference: TDD Triggers

| 场景 | TDD 动作 | 原因 |
|------|---------|------|
| 新功能开发 | 先写测试 | 用测试定义功能的预期行为 |
| Bug 修复 | 先写复现测试 | 确保修复前 Bug 确实存在，修复后不会复现 |
| 代码重构 | 确保已有测试通过 | 重构不改变行为，用测试做安全网 |
| 覆盖率 < 80% | 补充缺失测试 | 发现未覆盖的代码路径 |

## Pre-Implementation Checklist

在开始写任何实现代码之前：
- [ ] 测试文件已创建（与源文件同目录或镜像目录结构）
- [ ] 首个测试用例已编写（只覆盖一个行为）
- [ ] 运行测试并确认失败（RED 阶段确认）
- [ ] 失败原因符合预期（功能未实现，而非语法错误）
- [ ] 已确认需要 Mock 的外部依赖

---

## Post-Implementation Checklist

在所有功能实现之后：
- [ ] 所有测试通过（GREEN 确认）
- [ ] 代码已经过重构优化（消除重复、改善命名）
- [ ] 覆盖率 >= 80%
- [ ] 边界条件和错误路径已覆盖
- [ ] 测试命名清晰描述被测试的行为
- [ ] Mock 使用合理（未 Mock 被测试代码本身）

---

## How to Use This Guide

1. **新功能开发前**：阅读 RED 阶段，确保从测试开始
2. **开发过程中**：严格遵循 RED → GREEN → REFACTOR 三步循环
3. **代码审查时**：检查是否满足 Pre/Post-Implementation Checklist
4. **Bug 发生时**：回顾 Common TDD Mistakes，找出流程违规

---

**核心原则**：测试不是在实现后验证代码，而是在实现前定义行为。
