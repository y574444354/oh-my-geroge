# /workflow — 完整开发流水线

## 概述

oh-my-costrict 的核心开发流水线。按顺序执行 8 个 Phase，每个 Phase 之间有 Gate 检查，确保质量门控。所有 Phase 都可作为独立 `/oh-my-costrict:xxx` 命令单独调用。

## 流水线全景

```
/workflow <任务描述>
      │
      ▼
┌──────────────────────────────────────────────────────────────────┐
│ Phase 1: 需求探索 + PRD 生成        独立命令: /prd                 │
│   委托 planner agent                                              │
│   内置 grill-with-docs（挑战业务需求 + 术语定义）                    │
│   产出：PRD 文档 + CONTEXT.md 术语更新                             │
│   🚦 Gate: PRD 审查通过？→ 继续 / 修改 / 终止                      │
└──────────────────────────────────────────────────────────────────┘
      ↓
┌──────────────────────────────────────────────────────────────────┐
│ Phase 2: UI 设计 + 审查 [条件触发]                                 │
│   委托 ui-ux-pro-max skill（检测到前端/UI 关键词时触发）             │
│   产出：UI 设计系统推荐 + 审查报告                                   │
│   🚦 Gate: 设计审查通过？→ 继续 / 修改 / 跳过                       │
│   ⚠️ 非前端任务（纯后端/CLI/库）→ 自动跳过此 Phase                   │
└──────────────────────────────────────────────────────────────────┘
      ↓
┌──────────────────────────────────────────────────────────────────┐
│ Phase 3: 架构设计 + 审查            独立命令: /design               │
│   委托 architect agent                                            │
│   内置 grill-with-docs（挑战技术选型 + 架构决策）                     │
│   产出：技术方案文档 + ADR                                          │
│   🚦 Gate: 架构审查通过？→ 继续 / 修改 / 终止                       │
└──────────────────────────────────────────────────────────────────┘
      ↓
┌──────────────────────────────────────────────────────────────────┐
│ Phase 4: 拆解编码子任务              独立命令: /plan                │
│   委托 planner agent（从 PRD + 设计 + 架构产出独立子任务）            │
│   按垂直切片拆分，每个子任务可独立编码和测试                           │
│   产出：子任务列表（优先级排序 + 依赖关系标记）                        │

      ↓
┌──────────────────────────────────────────────────────────────────┐

│   产出：审查报告（CRITICAL/HIGH/MEDIUM/LOW 分级，含独立 DX 章节）     │

      ↓
┌──────────────────────────────────────────────────────────────────┐

│   根据 Phase 6 审查报告，executor 修复 → reviewer 再审              │

│   超过 3 轮仍未通过 → 报告阻塞                                      │
└──────────────────────────────────────────────────────────────────┘
      ↓
┌──────────────────────────────────────────────────────────────────┐
│ Phase 8: 验证 + 汇总报告             独立命令: /verify              │
```

## 各 Phase 详细说明

### Phase 1: 需求探索 + PRD 生成

委托 **oh-my-costrict:planner** agent 执行：
- 分析用户的任务描述，阅读项目代码库
- 内置 grill-with-docs 术语挑战（提取关键术语 → 精确定义 → 更新 CONTEXT.md）
- 产出结构化 PRD 文档

**输入**：用户的原始任务描述
**输出**：`# PRD: <任务标题>` 文档（包含目标、范围、验收标准、技术约束、实现步骤、风险点、术语对齐表）

**🚦 Gate 检查**：PRD 生成后，列出以下关键决策点询问用户确认：
1. 范围和边界是否正确？
2. 验收标准是否清晰可测？
3. 技术约束是否合理？
4. 术语定义是否与业务对齐？

- 用户全部确认 → 进入 Phase 2
- 用户要求修改 → 回到 planner 修改 PRD，修改后重新 Gate
- 用户选择终止 → 结束流水线，输出已产生的 PRD 文档

### Phase 2: UI 设计 + 审查 [条件触发]

**自动判断任务类型**：

检测 PRD 中是否包含前端/UI 相关关键词（如：页面、组件、UI、前端、界面、交互、样式、CSS、HTML、布局、响应式、动画、Dashboard、表单、按钮、导航、弹窗、列表等）。

- **命中关键词（前端/全栈任务）** → 触发此 Phase
- **未命中（纯后端/CLI/库）** → 跳过此 Phase，直接进入 Phase 3

**触发时执行**：

委托 **oh-my-costrict:ui-ux-pro-max** skill 执行：
- 基于 PRD 需求推荐 UI 设计系统（风格、调色板、字体、UX 准则）
- 输出视觉设计建议和审查报告

**输入**：Phase 1 的 PRD 文档
**输出**：`# UI 设计审查报告`（设计系统推荐 + UX 准则 + 改进建议）

**🚦 Gate 检查**：设计审查通过后，列出关键设计决策询问用户：
1. 设计风格和调色板是否合适？
2. UX 准则是否覆盖主要交互场景？
3. 是否有需要调整的设计建议？

- 用户全部确认 → 进入 Phase 3
- 用户要求修改 → 调整设计建议，重新 Gate
- 用户选择跳过 → 进入 Phase 3（保留设计报告作为参考）

### Phase 3: 架构设计 + 审查

委托 **oh-my-costrict:architect** agent 执行：
- 基于 PRD（+ UI 设计报告，如有）设计技术方案
- 内置 grill-with-docs 领域验证（挑战技术选型、架构决策、术语一致性）
- 必要时生成 ADR（满足三条件：难以逆转 + 缺少上下文会困惑 + 真正做过取舍）

**输入**：Phase 1 的 PRD + Phase 2 的设计报告（如有）
**输出**：`# 技术方案: <标题>` 文档 + ADR（如适用）

**🚦 Gate 检查**：架构方案产出后，列出关键架构决策询问用户：
1. 技术选型是否合理？（每项选型附带备选方案和取舍理由）
2. 模块划分和数据流是否清晰？
3. ADR（如有）中的决策是否可接受？
4. grill-with-docs 验证出的问题是否已处理？

- 用户全部确认 → 进入 Phase 4
- 用户要求修改 → 回到 architect 修改方案，修改后重新 Gate
- 用户选择终止 → 结束流水线，输出已产生的所有文档

### Phase 4: 拆解编码子任务

委托 **oh-my-costrict:planner** agent 执行：
- 读取 Phase 1-3 的全量产出（PRD + UI 设计 + 技术方案 + ADR）
- 按垂直切片原则拆解为独立子任务
- 标注依赖关系和并行能力

**拆解原则**：

- **垂直切片**：每个子任务是完整的功能切片（从前端到后端），而非按技术层拆分
  - 好的拆法："实现用户登录功能（含前端表单 + 后端验证 + Token 管理）"
  - 不好的拆法："实现用户控制器"、"实现用户服务层"
- **独立可编码**：单一开发者可在 1-3 小时内完成
- **独立可测试**：有明确的验收条件
- **依赖标记**：
  - 无依赖 → 标记"可并行"
  - 硬依赖 → 标记"依赖 [子任务 N]"
  - 软依赖 → 标记"建议在 [子任务 N] 之后"

**输入**：Phase 1-3 的所有文档
**输出**：`# 编码子任务列表`（优先级排序 + 依赖关系图 + 并行执行计划）

### Phase 5: TDD 编码

委托 **oh-my-costrict:tdd-guide** agent 引导编码，委托 **oh-my-costrict:executor** agent 执行编码。

**并行策略**：

根据 Phase 4 产出的依赖关系图，分批执行：

1. **第一波**：所有"可并行"（无依赖）的子任务同时启动 executor
2. **第二波**：依赖第一波的子任务（第一波完成后立即启动）
3. **第三波及后续**：依次按依赖关系执行

每个 executor 实例严格遵循 TDD 循环（RED → GREEN → REFACTOR）：
- 先写测试 → 确认失败
- 编写最简实现 → 确认通过
- 重构改进 → 保持通过

**输入**：Phase 1-4 的全部文档
**输出**：代码文件 + 测试文件 + TDD 完成报告

### Phase 6: 代码审查 + DX 审查

委托 **oh-my-costrict:reviewer** agent 执行，从两个视角审查：

#### 代码质量审查
- 命名规范、代码结构、注释质量
- 设计合理性（单一职责、接口设计、依赖关系）
- 安全性（硬编码密钥、输入验证、注入风险、权限检查）

#### DX（开发者体验）审查（作为审查报告的独立章节）
- API 易用性：函数签名是否直观、参数是否合理
- 文档完整性：是否有必要的使用示例和说明
- 错误信息友好度：错误消息是否清晰可操作
- 配置复杂度：上手成本是否合理

**输入**：Phase 5 产出的代码 + 测试
**输出**：`# 代码审查报告`（问题按 CRITICAL/HIGH/MEDIUM/LOW 分级，DX 审查为独立章节）

### Phase 7: 修复循环

根据 Phase 6 的审查报告，进入修复循环：

```
审查报告
    │
    ├─ 无 CRITICAL/HIGH 问题 → 直接进入 Phase 8 ✅
    │
    └─ 有 CRITICAL/HIGH 问题 → executor 修复
                                 │
                                 └─ reviewer 再审
                                      │
                                      ├─ 通过 → 进入 Phase 8 ✅
                                      │
                                      └─ 仍有问题 → 继续修复（第 2 轮）
                                           │
                                           ├─ 通过 → 进入 Phase 8 ✅
                                           │
                                           └─ 仍有问题 → 继续修复（第 3 轮）
                                                │
                                                ├─ 通过 → 进入 Phase 8 ✅
                                                │
                                                └─ 仍不通过 → 报告阻塞 ❌
```

**规则**：
- 最多 3 轮修复循环
- 任一轮审查通过（无 CRITICAL/HIGH 问题）即跳出循环
- 超过 3 轮仍未通过 → 报告阻塞原因，询问用户是否人工介入或降低标准
- 仅修复 CRITICAL 和 HIGH 问题，MEDIUM/LOW 问题记录但不阻塞

### Phase 8: 验证 + 汇总报告

委托 **oh-my-costrict:verifier** agent 执行：
- 运行测试 + 覆盖率检查（目标 >= 80%）
- Lint / TypeCheck 检查
- 失败则委托 executor 修复并重跑（最多 3 轮）

全部检查通过后，汇总全流程产出。

**输入**：Phase 5-7 的所有代码和报告
**输出**：验证报告 + 全流程汇总报告

## 使用方式

```bash
# 完整流水线（前端/全栈任务）
/oh-my-costrict:workflow 实现用户仪表盘页面，包含数据图表和用户设置表单

# 完整流水线（纯后端任务，自动跳过 Phase 2）
/oh-my-costrict:workflow 实现用户认证 API，包含 JWT 令牌管理和密码加密
```

## 注意事项

- 流水线按 Phase 1→2→3→4→5→6→7→8 严格串行执行
- Phase 2 条件触发：检测到前端/UI 关键词时执行，否则自动跳过
- 每个 Phase 的 🌉 Gate 需要用户确认，不通过则修改后重试或终止
- 任一 Gate 用户选择"终止" → 结束流水线，已产出的文档保留
- Phase 5 的并行策略：无依赖子任务同时执行，有依赖的按顺序执行
- Phase 7 最多 3 轮修复循环，超过则报告阻塞
- 所有输出使用中文
