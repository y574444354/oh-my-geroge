# /tdd — TDD 开发

## 概述

委托 tdd-guide agent 执行完整的测试驱动开发循环。严格遵循 RED（写失败测试）→ GREEN（最简实现）→ REFACTOR（重构改进）三步循环，每次迭代输出阶段报告和覆盖率数据。

## 执行流程

### 委托 tdd-guide agent

委托 **oh-my-costrict:tdd-guide** agent 执行完整的 TDD 流程：

#### 循环 1: 分析需求，编写首个测试

**RED 阶段**：
1. 分析功能需求，确定首个测试行为
2. 编写最小、最聚焦的测试用例
3. 运行测试 —— **确认测试失败**（这是关键！）
4. 输出 RED 阶段报告

**GREEN 阶段**：
1. 编写**刚好足以让测试通过**的最简代码
2. 不写任何额外功能 —— 只让测试变绿
3. 运行测试 —— 确认通过
4. 输出 GREEN 阶段报告

**REFACTOR 阶段**：
1. 在测试保护下重构代码
2. 消除重复、改善命名、提取函数
3. 运行测试 —— 确认所有测试仍通过
4. 输出 REFACTOR 阶段报告

#### 循环 2..N: 持续迭代

重复 RED → GREEN → REFACTOR 循环，每次迭代：
- 添加新的测试用例（覆盖新行为或边界条件）
- 实现以通过新测试
- 在测试保护下重构
- 输出每次循环的阶段报告 + 覆盖率变化

#### 覆盖率检查

每次循环后检查覆盖率：
- 行覆盖率 >= 80%
- 分支覆盖率 >= 80%
- 函数覆盖率 >= 80%
- 不达标则继续迭代，添加缺失场景的测试


## 反模式警告

tdd-guide agent 将自动检测并警告以下反模式：
- **先写代码后补测试**：违反 TDD 根本原则
- **一次写大量测试**：应该小步快跑
- **跳过 RED 阶段**：必须确认测试先失败
- **测试过于复杂**：测试代码应比实现代码简单
- **依赖外部状态**：测试应独立运行
- **测试实现细节**：应测试行为而非实现

## 使用方式

```bash
# 从零开始 TDD 开发
/tdd 实现用户密码重置功能

# 为现有模块添加 TDD 覆盖
/tdd 为 src/utils/validator.ts 添加测试
```

## 注意事项

- 委托 tdd-guide agent，不要自行执行 TDD
- 严格遵守 RED → GREEN → REFACTOR 顺序，不可跳步
- 最小步长：每次只添加一个测试、一段最小实现
- 测试即文档：测试用例应清楚描述模块行为
- 所有输出使用中文
