# /prd — PRD 生成

## 概述

委托 planner agent 分析需求并产出结构化 PRD 文档。内置 grill-with-docs 指令，在 PRD 生成过程中挑战业务需求和术语定义，必要时更新 CONTEXT.md。PRD 生成后进入 Gate 检查，列出关键决策点询问用户确认，不通过则修改后重试。

对应完整流水线 Phase 1。

## 执行流程

### Step 1: 委托 planner agent

委托 **oh-my-costrict:planner** agent 分析任务需求，阅读项目代码库，产出结构化 PRD。

planner 的输出应包含：
- **目标**：要解决的问题或实现的功能
- **范围**：明确包含和不包含的内容
- **验收标准**：可验证的完成条件
- **技术约束**：语言、框架、依赖、性能要求
- **实现步骤**：按依赖顺序排列的子任务列表
- **风险点**：已知风险和缓解措施

### Step 2: grill-with-docs 术语挑战（内置）

在 planner 产出 PRD 后，自动执行 grill-with-docs 术语挑战：

1. 从 PRD 中提取所有关键术语
2. 检查 CONTEXT.md（如不存在则跳过）
3. 对每个术语进行精确定义挑战：
   - 这个术语是否模糊或过载？
   - 这个术语的业务含义是什么？
   - 这个术语和代码库中的命名一致吗？
4. 术语确定后立即更新 CONTEXT.md（惰性创建）
5. 输出术语对齐报告

### Step 3: 输出 PRD 草稿

将 planner 产出的 PRD + grill-with-docs 术语挑战结果合并，输出为 PRD 草稿。

### Step 4: 🚦 Gate 检查 — 关键决策确认

PRD 草稿输出后，列出以下关键决策点，询问用户确认：

```
🚦 PRD Gate — 请确认以下关键决策：

1. **范围和边界**：PRD 中定义的范围是否正确？是否有遗漏或多余的部分？
2. **验收标准**：验收标准是否清晰可测？是否覆盖了核心场景和边界条件？
3. **技术约束**：技术约束是否合理？是否有未声明的限制？
4. **术语定义**：grill-with-docs 术语对齐结果是否准确？术语定义是否与业务一致？
5. **风险识别**：列出的风险点是否完整？缓解措施是否可行？

请回复：
- "通过" / "确认" → 进入下一阶段
- "修改 <具体修改意见>" → 根据意见修改 PRD 并重新 Gate
- "终止" → 结束流程，保留当前 PRD 文档
```

**Gate 规则**：
- 用户全部确认 → PRD 定稿，进入下一阶段
- 用户要求修改 → 回到 planner 按意见修改，修改后重新 Gate
- 用户选择终止 → 结束流程，输出已产生的 PRD 文档作为参考
- Gate 循环次数不限，直到用户确认通过或选择终止

## 输出格式

```markdown

## 基础信息
- 任务 ID: ...
- 规划日期: ...
- 状态: 草稿 / 已确认

## 目标
...

## 范围
- 包含：...
- 不包含：...

## 验收标准
- [ ] ...
- [ ] ...

## 技术约束
...

## 实现步骤
1. [子任务1] - 可并行
2. [子任务2] - 可并行
3. [子任务3] - 依赖步骤1

## 风险点
- ...

## 术语对齐（grill-with-docs）
| 术语 | 原用法 | 精确定义 | 状态 |
|------|--------|----------|------|
| ... | ... | ... | ✅ / ⚠️ |
```

## 使用方式

```bash
# 在 workflow 流水线中自动触发（Phase 1）
/oh-my-costrict:workflow 实现用户认证系统

# 独立调用
/oh-my-costrict:prd 实现用户认证系统，包含登录、注册和密码重置
```

## 注意事项

- 委托 planner agent，不要自行生成 PRD
- grill-with-docs 术语挑战是内置步骤，自动执行无需手动触发
- CONTEXT.md 不存在时惰性创建
- Gate 检查必须列出具体的关键决策点，而非简单的是/否问题
- Gate 不通过时提供明确的修改方向
- 所有输出使用中文
