# /grill-with-docs — 领域模型驱动的设计审查

## 概述

基于 Matt Pocock grill-with-docs 模式，适配 oh-my-costrict 的 spec 体系。对 PRD / 技术方案进行"无情面试"，用项目已有的领域模型、术语表和架构决策记录来挑战方案的每个分支。同时负责更新 CONTEXT.md 术语表和生成 ADR。

## 核心规则

1. **无情面试**：对设计方案的每个分支进行追问，直到所有决策都被解决
2. **领域模型优先**：先用项目已有的 spec 和 CONTEXT.md 挑战方案，再提新问题
3. **术语精确化**：发现模糊/过载术语时立即提出精确定义
4. **代码库验证**：能用代码库回答的问题，优先探索代码库而非询问用户
5. **一次一问**：每次只问一个问题，附带推荐答案
6. **内联更新**：术语确定后立即更新 CONTEXT.md，不等到最后批量写

## 触发时机

以下情况自动触发（无需用户手动调用）：

| 触发条件 | 触发方式 |
|----------|----------|
| `/costrict-autopilot` 进入设计审查阶段 | 自动作为 Phase 2b 执行 |
| PRD 确认后进入架构设计 | 自动触发 |
| 用户说 "review the design" / "审查设计" / "grill my plan" | 手动触发 |
| 任务涉及跨模块/跨层变更 | 自动判断触发 |

## 执行流程

### Step 0: 加载领域模型

开始前，读取以下文件建立领域认知：

```
# 项目 spec 体系（oh-my-costrict 的"领域模型"）
.trellis/spec/backend/index.md          # 后端规范索引
.trellis/spec/frontend/index.md         # 前端规范索引
.trellis/spec/guides/index.md           # 跨层思维指南

# 项目术语表（如果存在）
CONTEXT.md                               # 全局术语表

# 架构决策记录（如果存在）
docs/adr/                                # ADR 目录
```

如果 CONTEXT.md 不存在，在审查过程中按需创建（惰性创建 — 只有第一个术语确定后才创建）。

### Step 1: 术语挑战

从 PRD / 设计方案中提取所有关键术语，逐一挑战：

```
对每个术语问三个问题：
1. 这个术语在 CONTEXT.md 中已有定义吗？→ 有则检查一致性
2. 这个术语是否模糊或过载？→ 是则提出精确定义
3. 这个术语和代码库中的实际命名一致吗？→ 不一致则指出
```

**示例**：
- PRD 说 "用户" → 是 Customer 还是 User？是登录用户还是匿名访客？
- PRD 说 "订单状态" → 有哪些状态？状态机是什么？和数据库 schema 一致吗？

### Step 2: 领域关系挑战

用具体场景压力测试领域关系：

```
对每个领域关系：
1. 一个 X 可以有多个 Y 吗？
2. Y 可以独立于 X 存在吗？
3. X 和 Y 之间的边界在哪里？
4. 什么场景下这个关系会断裂？
```

**场景驱动**：编造边界场景来迫使精确化
- "如果一个用户同时属于两个团队，权限怎么算？"
- "如果订单在支付完成前被取消，库存什么时候释放？"

### Step 3: 架构决策挑战

对方案中的每个架构选择进行追问：

```
对每个架构决策：
1. 为什么选 A 而不是 B？（必须有明确的 trade-off 分析）
2. 这个决策以后能改吗？改的成本多大？
3. 如果没有这个上下文，后来者会困惑吗？
4. 有没有真正的备选方案被考虑过？
```

**ADR 触发条件**（三个条件同时满足才生成 ADR）：
1. **难以逆转** — 后面改这个决策有实际成本
2. **缺少上下文会令人困惑** — 后来者看到代码会纳闷"为什么这样？"
3. **真正做过取舍** — 存在真实的备选方案，且为特定原因选了其中一个

缺少任一条件 → 跳过 ADR，不生成。

### Step 4: 代码库一致性验证

```
对方案中的每个声明：
1. "我们目前是这样做的" → 验证代码库是否真的这样做
2. "XX 模块已经支持了" → 验证 .trellis/spec/ 和源码
3. "用现有的 XX 模式" → 确认模式确实存在且适用
```

矛盾立即指出："你说 X，但代码库里是 Y —— 哪个是对的？"

### Step 5: 内联更新

#### 更新 CONTEXT.md

术语确定后**立即**写入，不批量：

```markdown
## <术语名>
- **定义**：<一句话精确定义>
- **区别于**：<容易混淆的概念>
- **首次使用于**：<PRD/任务名>
```

CONTEXT.md 必须是**纯术语表**，不包含：
- ❌ 实现细节
- ❌ 技术规格
- ❌ TODO 列表
- ❌ 临时代码片段

#### 生成 ADR

满足触发条件时，写入 `docs/adr/NNNN-<slug>.md`：

```markdown
# ADR-NNNN: <标题>

## 状态
提议 / 已采纳 / 已废弃

## 上下文
<为什么需要做这个决策>

## 决策
<选择了什么>

## 备选方案
<考虑过但没选的方案及原因>

## 后果
<正面和负面的影响>
```

### Step 6: 输出审查报告

审查完成后输出结构化报告：

```markdown
## 设计审查报告 (grill-with-docs)

### 术语对齐
| 术语 | 原用法 | 精确定义 | 状态 |
|------|--------|----------|------|
| ... | ... | ... | ✅ 已更新 / ⚠️ 待确认 |

### 领域关系验证
- ✅ 已确认的：...
- ⚠️ 需要澄清的：...

### 架构决策
| 决策 | ADR | 状态 |
|------|-----|------|
| ... | ADR-0001 | 📝 已记录 |

### 代码库一致性
- ✅ 一致的：...
- ⚠️ 矛盾的：...

### 整体评估
- 通过 / 需修改 / 需重新设计
```

## 与其他技能的协作

```
grill-with-docs 在设计审查阶段运行：
  Phase 1: PRD 生成 (planner + grill-me 内置在 brainstorm)
  Phase 2a: UI 设计审查 (ui-ux-pro-max) ← 条件触发
  Phase 2b: 架构设计审查 (grill-with-docs) ← 始终触发 ★
  Phase 3: 工程审查 (reviewer)
  Phase 4: DX 审查 (reviewer)
  Phase 5: 汇总报告
```

## 反模式

- ❌ 跳过代码库验证直接相信 PRD 中的说法
- ❌ 发现术语模糊但不追问
- ❌ 为每个决策生成 ADR（只有满足三条件才生成）
- ❌ 把 CONTEXT.md 写成技术文档或 TODO 列表
- ❌ 一次问多个问题
- ❌ 不问推荐答案的开放式问题

## 注意事项

- 审查深度与任务复杂度成正比：简单任务（1-2文件）轻量审查，复杂任务（跨模块）深度审查
- CONTEXT.md 如不存在，惰性创建（第一个术语确定后才创建文件）
- docs/adr/ 目录如不存在，第一个 ADR 生成时才创建
- 所有输出使用中文
