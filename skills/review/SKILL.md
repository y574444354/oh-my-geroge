# /review — 代码审查 + DX 审查

## 概述

委托 reviewer agent 对代码进行全面审查，覆盖代码质量、设计合理性、安全性、以及开发者体验（DX）四个维度。输出按 CRITICAL/HIGH/MEDIUM/LOW 分级的问题列表，每个问题附带具体修复建议。DX 审查作为审查报告的独立章节。

对应完整流水线 Phase 6。

## 执行流程

### 委托 reviewer agent

委托 **oh-my-costrict:reviewer** agent，执行以下审查：

#### 1. 代码质量审查

- **命名规范**：变量、函数、类命名是否清晰、一致
- **代码结构**：函数是否短小（<50 行）、文件是否专注（<800 行）、嵌套是否过深（>4 层）
- **代码重复**：是否存在可提取的公共逻辑
- **注释质量**：注释是否准确、必要，中文注释是否规范
- **不可变性**：是否遵循不可变模式（创建新对象而非修改）

#### 2. 设计审查

- **单一职责**：每个模块/函数是否专注一件事
- **接口设计**：函数签名是否清晰、参数是否合理
- **依赖关系**：是否存在循环依赖、不合理的耦合
- **扩展性**：新增类似功能是否需要大量修改

#### 3. 安全审查

- **硬编码密钥**：检查是否存在 API key、密码、token
- **输入验证**：所有用户/外部输入是否经过验证
- **注入风险**：SQL 注入、XSS、命令注入
- **权限检查**：敏感操作是否有认证/授权
- **敏感数据泄露**：错误消息、日志是否泄露敏感信息

#### 4. DX（开发者体验）审查

DX 审查作为审查报告的独立章节，聚焦于代码的使用者体验：

- **API 易用性**：
  - 函数签名是否直观？参数数量是否合理？
  - 是否有合理的默认值？常见场景是否只需最少配置？
  - 导出的公共 API 是否简洁？内部实现细节是否被隐藏？

- **文档完整性**：
  - 公共 API 是否有 JSDoc/TSDoc 注释？
  - 是否有使用示例说明常见场景？
  - README 或模块级文档是否涵盖快速上手和常见问题？

- **错误信息友好度**：
  - 抛出的错误是否包含足够的上下文信息？
  - 错误消息是否指明了"用户应该怎么做"？
  - 错误类型是否有区分度（便于程序捕获处理）？

- **配置复杂度**：
  - 上手需要多少配置步骤？
  - 配置项是否有合理的默认值？
  - 配置的命名和组织是否清晰？

## 使用方式

```bash
# 在 workflow 流水线中自动触发（Phase 6）
/oh-my-costrict:workflow 实现用户仪表盘

# 独立调用 — 审查指定路径的代码
/oh-my-costrict:review src/components/Dashboard.tsx

# 独立调用 — 审查最近修改的代码
/oh-my-costrict:review 审查最近的提交
```

## 注意事项

- 委托 reviewer agent，不要自行审查
- 客观公平：审查基于标准，非个人偏好
- 建设性：每个问题都附带具体的修复建议
- 优先级明确：不将 LOW 问题标注为 HIGH
- 关注影响：优先关注影响用户和安全性的大问题
- DX 审查是代码审查的独立章节，无需单独命令
- 所有输出使用中文
